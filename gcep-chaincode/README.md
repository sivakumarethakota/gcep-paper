# `gcep` chaincode

Hyperledger Fabric 2.x chaincode implementing the GCEP smart contract from §3.6 of the paper. Three transactions, one query:

- `Write(c, bid, policy, sigP, m, r)` — Algorithm 1. Records a chameleon commitment.
- `Erase(c, bid, zkProof)` — Algorithm 3, Phase B. Validates patient ZK proof; flips status to `PENDING_ERASURE`.
- `FinaliseErase(c, mPrime, rPrime, sigC)` — Algorithm 3, Phase D. Validates committee threshold signature; rewrites pre-image; flips status to `ERASED`.
- `GetCommitment(c)` — read-only state query.

Plus three event emissions:

- `Written` — on every successful `Write`.
- `EraseRequested` — on `Erase` (so committee daemons wake up).
- `Erased` — on `FinaliseErase` (audit trail).

## Build

```bash
cd gcep-chaincode
go mod download
go test ./...                    # unit tests, no Fabric required
go vet ./...
go build ./cmd/gcep              # produces a self-contained binary
```

## Two trust roots

This chaincode embeds two pieces of cryptographic state at deploy time:

1. **`internal/zkverify/verifying.key`** — the Groth16 verifying key for the R_own circuit. Generated by `gcep/circuits/cmd/setup`. Anyone can verify a proof; nobody can forge one without the proving key.
2. **`internal/chameleon/pubkey.json`** — the threshold chameleon public key `y = g^x` (in BN254 G1). Generated by the committee's DKG. The trapdoor `x` is split across the committee; no single party holds it.

Both files **must be regenerated for production** — the dev defaults committed here are predictable. See `circuits/README.md` and §3.5.1 of the paper.

## Lifecycle deploy

Use the `gcep-local/scripts/deploy-chaincode.sh` driver:

```bash
cd ../gcep-local
./scripts/deploy-chaincode.sh ../gcep-chaincode
```

That script handles `peer lifecycle chaincode {package,install,approve,commit}` for both orgs.

## Endorsement policy

The contract is designed for `AND('HospitalMSP.peer','RegulatorMSP.peer')`. This guarantees:

- No single hospital can write a commitment that the regulator hasn't seen.
- No single regulator can finalise an erasure without hospital endorsement.

Set this at commit time via `--signature-policy` (the deploy script does so by default).

## What's intentionally NOT here

- The committee threshold-BLS daemon (separate Go binary; subscribes to `EraseRequested` events, runs the threshold session, submits `FinaliseErase`).
- The off-chain IPFS write/delete logic (lives in the hospital's application server, not the chaincode).
- The CP-ABE key derivation (lives in the hospital's KMS).

The chaincode is the **trust kernel** — it deliberately does as little as possible. Everything that doesn't need to be on-chain isn't.
